# 要求定義: 注文エンドポイント実装

## 概要
OrderHub（注文管理システム）の注文管理機能を実装する。カート内容からの注文作成、注文詳細取得、ステータス更新、キャンセル処理を含む4つのエンドポイントを、DDDレイヤードアーキテクチャに従って実装する。

## 実装対象エンドポイント

### 1. POST /api/v1/orders - 注文作成
カート内容をもとに注文を作成し、在庫引当・割引計算・合計金額算出を行う。

**入力**
- 顧客ID
- 配送先住所ID
- 注文商品リスト（商品ID、数量）
- クーポンコード（任意）

**処理内容**
- 顧客情報と配送先住所の検証
- 商品情報の取得と在庫確認
- 在庫引当処理
- 割引計算（会員ランク割引、数量割引、クーポン割引）
- 税込合計金額の計算
- 注文データの永続化
- OrderPlacedイベントの発行

**出力**
- 注文ID、ステータス、注文明細、金額情報、配送先情報、注文日時

### 2. GET /api/v1/orders/{order_id} - 注文詳細取得
指定された注文の詳細情報を取得する。

**入力**
- 注文ID（パスパラメータ）

**処理内容**
- 注文データの取得
- 注文明細のEager Loading

**出力**
- 注文詳細情報（POST時と同一構造）

### 3. PUT /api/v1/orders/{order_id}/status - 注文ステータス更新
注文のステータスを次の状態に遷移させる。

**入力**
- 注文ID（パスパラメータ）
- 新しいステータス

**処理内容**
- 注文の取得
- ステータス遷移の妥当性検証
- ステータス更新
- OrderShippedイベントの発行（SHIPPED時）

**出力**
- 注文ID、変更前ステータス、変更後ステータス、更新日時

### 4. POST /api/v1/orders/{order_id}/cancel - 注文キャンセル
注文をキャンセルし、在庫を戻す。

**入力**
- 注文ID（パスパラメータ）
- キャンセル理由

**処理内容**
- 注文の取得
- キャンセル可否の判定（CONFIRMED/PAID/PREPARINGのみ可）
- 引当済み在庫の解放
- 注文ステータスをCANCELLEDに更新
- OrderCancelledイベントの発行

**出力**
- 注文ID、ステータス、キャンセル理由、キャンセル日時

## 受け入れ条件

### 機能要件
- [ ] 4つのエンドポイントが正常に動作すること
- [ ] 在庫引当処理が正しく行われること（在庫不足時はエラー）
- [ ] 割引計算が仕様通りに実行されること（会員ランク→数量→クーポンの順）
- [ ] ステータス遷移が仕様に従って制御されること
- [ ] キャンセル時に在庫が正しく戻されること
- [ ] ドメインイベントが適切に発行されること

### 品質要件
- [ ] DDDレイヤードアーキテクチャに準拠すること
- [ ] 各層の責務が明確に分離されていること
- [ ] トランザクション境界が適切に管理されていること
- [ ] バリデーションがPresentation層で実行されること
- [ ] ビジネスルールがDomain層に集約されていること

### エラーハンドリング
- [ ] CUSTOMER_NOT_FOUND - 顧客IDが存在しない
- [ ] PRODUCT_NOT_FOUND - 商品IDが存在しない
- [ ] INSUFFICIENT_STOCK - 在庫不足
- [ ] INVALID_COUPON - クーポンが無効または期限切れ
- [ ] INVALID_SHIPPING_ADDRESS - 配送先住所が顧客に紐付いていない
- [ ] ORDER_NOT_FOUND - 注文IDが存在しない
- [ ] INVALID_STATUS_TRANSITION - 許可されないステータス遷移
- [ ] ORDER_CANNOT_BE_CANCELLED - 出荷済み/配達完了の注文

## 制約事項

### 技術的制約
- 既存のDDDレイヤードアーキテクチャに従うこと
- 既存のcustomer、product、stock境界づけられたコンテキストと連携すること
- FastAPI + SQLAlchemyを使用すること
- Pydanticでリクエスト/レスポンスのバリデーションを行うこと

### ビジネス的制約
- ステータス遷移ルール:
  - CONFIRMED → PAID → PREPARING → SHIPPED → DELIVERED
  - 上記以外の遷移は不可
- キャンセル可能ステータス: CONFIRMED, PAID, PREPARING
- 割引適用順序: 会員ランク割引（小計） → 数量割引（商品単位） → クーポン割引（最終合計）

### データ整合性
- 注文作成と在庫引当は同一トランザクション内で実行すること
- 注文キャンセルと在庫解放は同一トランザクション内で実行すること
- 在庫の引当・解放は排他制御を考慮すること

## 依存関係

### 既存コンポーネントへの依存
- **Customer境界コンテキスト**
  - CustomerRepository（顧客取得、配送先住所検証）
  - Customerエンティティ

- **Product境界コンテキスト**
  - ProductRepository（商品情報取得）
  - Productエンティティ
  - Price値オブジェクト

- **Stock境界コンテキスト**
  - StockRepository（在庫取得、更新）
  - Stockエンティティ（allocate、releaseメソッド）

### 新規作成コンポーネント
- **Order境界コンテキスト**（新規）
  - Orderエンティティ（集約ルート）
  - OrderItemエンティティ
  - OrderStatus値オブジェクト
  - Money値オブジェクト（金額計算）
  - ShippingAddress値オブジェクト
  - OrderRepository
  - OrderDomainService（注文生成ロジック）
  - DiscountPolicy（割引ルール）

### インフラストラクチャ
- イベントバス（インメモリ実装）
- SQLAlchemyモデル（ordersテーブル、order_itemsテーブル）

## 備考
- 本実装は、既存のCustomer、Product、Stock機能が実装済みであることを前提とする
- ドメインイベントの購読者（イベントハンドラー）は別タスクで実装する
- クーポン機能の詳細（Couponエンティティ）は今回のスコープ外とし、簡易的な検証のみ実装する
- 配送料計算ロジックは固定値（500円）とする
