# テスト戦略まとめ

> Next.js 15 / FastAPI / PostgreSQL / AWS (ECS Fargate + Aurora)

---

## 1. テストフェーズの全体構成

ウォーターフォール開発における各テストフェーズの位置づけは以下の通りです。

| フェーズ | 目的 | 実施タイミング | 環境 |
|---|---|---|---|
| 単体テスト | 関数・コンポーネント単体の動作確認 | 実装と並行 | CI (GitHub Actions) |
| 結合テスト | コンポーネント間の連携確認 | 単体テスト完了後 | CI (GitHub Actions) |
| システムテスト（E2E） | ユーザーシナリオ全体の動作確認 | 結合テスト完了後 | Staging環境 |
| システムテスト（性能テスト） | SLA・ピーク負荷への耐性確認 | 結合テスト完了後〜システムテスト後半 | Staging環境（必須） |

---

## 2. フロントエンドのテスト観点

テスト観点は単体・結合・システムテスト共通のインプットです。洗い出した観点をどのフェーズで検証するかを振り分けます。

```
テスト観点（共通）
  ├── 単体テスト     → Client Componentの操作・ユーティリティ関数
  ├── 結合テスト     → Server Actions〜APIの連携・エラーレスポンスの表示
  └── システムテスト → ユーザーシナリオ全体
```

### ① 画面×機能のマトリクス

画面一覧と機能一覧を書き出して掛け合わせます。

- 画面例：ログイン / ダッシュボード / アセスメント回答 / 結果確認
- 機能例：表示 / 入力 / 送信 / バリデーション / 画面遷移

### ② 各機能への観点の当てはめ

| 観点 | 単体テスト | 結合テスト | システムテスト |
|---|---|---|---|
| 表示系 | Client Componentのレンダリング（モーダル開閉・タブ切り替えなど） | APIレスポンス→画面への反映 | シナリオ全体で正しく表示される |
| 入力・バリデーション | 必須項目未入力・形式チェック（zodのバリデーション関数） | バリデーションエラーのレスポンス表示 | 画面から入力して送信 |
| 権限・認証 | - | 未認証リクエスト→エラー表示 | 未認証アクセス→リダイレクト |
| 画面遷移 | - | - | 正しい遷移先・戻るボタン動作 |
| 境界値 | zodのバリデーション関数に境界値を渡す | 境界値データをAPIに送る | 画面から境界値を入力して送信 |
| 非機能 | - | - | レスポンシブ（スマホ・タブレット）・対応ブラウザ（Chrome / Safari / Edge） |

### ③ ユーザーシナリオから逆引き

ユーザーが「何をするためにこのシステムを使うか」を起点にシナリオを定義し、それをそのままシステムテストのテストケースにします。

### ④ ウォーターフォールでの進め方

- 基本設計フェーズ：画面・機能一覧からテスト観点のマトリクス作成
- 詳細設計フェーズ：観点を具体的なテストケースに落とし込む
- テストフェーズ：実施・エビデンス（スクリーンショット・ログ）取得

## 3. 単体テスト

### 3-1. フロントエンド（Next.js 15）

**ツール：** Jest + React Testing Library

**技術スタック：** shadcn/ui + zod + Server Actions（react-hook-formは不要）

#### Server Componentsのテスト方針

Next.js公式ドキュメントによると、**async Server ComponentsはJest・Vitestともに現時点でサポートされていない。** async Componentに対してはE2Eテストを推奨するとされている。

そのため、Server Componentsのテスト方針は以下の通りとする。

| 対象 | テスト方法 |
|---|---|
| Server Componentsの表示 | PlaywrightまたはE2E手動テスト |
| ビジネスロジック | **FastAPI側に寄せる**（フロントに複雑なロジックを持たない） |
| フォームバリデーション | Server Actions内でzodを使用。Jestでテスト可能 |
| ユーティリティ関数（日付フォーマット等） | Jest |

#### Client Componentのテスト方針

shadcn/uiを使うコンポーネントやイベントハンドラを持つコンポーネントはClient Componentにする必要がある。テスト対象は**「ユーザーが操作したらUIがどう変わるか」**に絞る。

| テスト対象 | 例 |
|---|---|
| フォームのバリデーション表示 | 必須項目が空のとき送信ボタンが無効になる |
| 表示の切り替え | ボタンを押すとモーダルが開く |
| 入力に応じたUI変化 | 全項目入力後に送信ボタンが有効になる |
| shadcn/uiコンポーネントの操作 | タブ切り替え・ドロップダウンの選択 |

APIコールは絡まないため、モック不要でシンプルに書ける。

#### Client Componentになる主なコンポーネント

| コンポーネント | 理由 |
|---|---|
| フォーム全般 | Server Actions + shadcn/ui（useActionState使用） |
| Dialog / Sheet | 開閉状態の管理 |
| DropdownMenu | 開閉状態の管理 |
| Toast（Sonner） | 通知の表示制御 |
| DataTable | ソート・フィルターの状態管理 |

> ページ全体をClient Componentにするのではなく、インタラクティブな部分だけを末端のClient Componentとして切り出す設計にするとテストが書きやすくなる。

### 3-2. バックエンド（FastAPI）

**ツール：** pytest

レイヤードアーキテクチャ + 戦術的DDDを採用しているため、**Domain層を中心に単体テストを書く**方針とする。外部依存が一切ないためモック不要で書けるケースが多い。

**Domain層（最重要）**

Entity・Value Object・Domain Serviceが対象。ビジネスロジックが集中しているため最も手厚くテストする。

| 対象 | テスト内容 |
|---|---|
| Entity / Value Object | 生成時のバリデーション・状態変化・ドメインルールの検証 |
| Domain Service | 複数Entityにまたがるロジック（Repositoryはモック） |

**Application層**

ユースケースの流れをテストする。Repository interfaceはモックに差し替える。

| 対象 | テスト内容 |
|---|---|
| Use Case | 正常系・異常系のユースケースの流れ |

**Presentation層・Infrastructure層は単体テスト不要**

Presentation層はルーティングの薄いラッパーなので結合テストでカバーする。Infrastructure層はDBが絡むため結合テストで検証する。

## 4. 結合テスト

### 4-1. フロントエンド（Next.js + FastAPI）

**ツール：** Jest + MSW（Mock Service Worker）

実際のAPIレスポンス形式に合わせたモックサーバーを立て、Server Actionsからの通信処理とUI表示まで検証します。バックエンドチームとレスポンス仕様を合わせておくことで結合テストの精度が向上します。

> Server Actionsを使う構成ではfetchの呼び出しもサーバー側で行われるため、MSWのインターセプト設定はサーバーサイド向けの設定が必要になります。

### 4-2. バックエンド（FastAPI + PostgreSQL）

**ツール：** pytest + SQLAlchemy + TestClient（FastAPI組み込み）

**実行環境：GitHub Actions（CI）**

GitHub Actions上でPostgreSQLサービスコンテナを立ち上げて実行します。CIのジョブが終わるたびに環境がリセットされるため、rollbackは不要です。

**テスト対象**

| レイヤー | テスト内容 |
|---|---|
| Infrastructure（Repository実装） | CRUD操作・DB制約・リレーションのマッピング・検索・フィルタリング |
| Presentation（APIエンドポイント） | リクエスト→レスポンスの検証・バリデーションエラー（422）・認証エラー（401）など |

**Repository実装のテストで確認すること**

- CRUD操作が正しく動くか
- UNIQUE制約などDB制約が正しく機能するか
- リレーション（関連データ）が正しくマッピングされるか
- 検索・フィルタリングが正しく動くか
- GSI経由の検索が正しく動くか（DynamoDB）

**GitHub Actions設定のポイント：**

- `services: postgres` でPostgreSQLコンテナを起動
- `--health-cmd pg_isready` でDB起動を待機
- Auroraのバージョンに合わせたPostgreSQLイメージを使用
- `alembic upgrade head` でマイグレーションを実行してからテスト

**テストコードのポイント：**

- `scope="function"` のfixtureでテスト間のDB汚染を防ぐ
- 件数に依存しない書き方にする（テストの実行順序に影響されない）

> PRを出すたびに自動でテストが走るようにCIを設定するとアウトプットの品質が向上します。

## 5. システムテスト（E2E）

### 5-1. フロントエンド E2E

**ツール：** Playwright（Next.jsとの公式統合が充実）

**E2E自動化の判断：**

| 状況 | 推奨方針 |
|---|---|
| 3人チームでリソースが限られる | 重要シナリオ5〜10本に絞ってPlaywright |
| リリース頻度が低い（ウォーターフォール） | 手動テストでも十分カバーできる |
| 認証など絶対壊せない箇所がある | その箇所だけE2E自動化 |

## 6. システムテスト（性能テスト）

### 6-1. 実施タイミング

結合テスト完了後から並行して開始し、システムテスト後半にかけて実施します。バグが残った状態での性能テストは原因特定が困難になるため、機能テストと並行して進めます。

| タイミング | やること |
|---|---|
| 結合テスト完了後 | Auroraのスロークエリ調査・インデックスチューニング |
| システムテスト中盤 | Locustで段階的に負荷をかけて基本的な性能確認 |
| システムテスト後半 | ピーク1万同時接続の本番相当テスト |

### 6-2. テストの種類と合格基準

判断基準は性能テスト前に決めておくこと。テスト後に決めると結果に対するバイアスが入りやすい。

**ストレステスト**

限界を超えるまで段階的に負荷を上げ続け、どの時点でエラーレートが上がり始めるかを観察する。

| 指標 | 合格基準 |
|---|---|
| エラーレート | 1万ユーザー時点で0.1%未満（SLA 99.9%から） |
| P95レスポンスタイム | 2秒以内 |
| P99レスポンスタイム | 5秒以内 |
| CPU使用率 | 80%未満 |
| DBコネクション数 | 上限の80%未満 |

**スパイクテスト**

Locustの LoadTestShape で負荷パターンをカスタマイズし、急激な増減に対してシステムが正しくスケールするかを確認する。

| 指標 | 合格基準 |
|---|---|
| スパイク中のエラーレート | 1%未満 |
| 正常状態への回復時間 | スパイク終了後60秒以内 |
| Auto Scalingの発動 | スパイク発生後3分以内にスケールアウト完了 |

**耐久テスト**

低〜中負荷（200ユーザー程度）で72時間回し続け、メモリリークやレスポンスタイムの劣化がないかを確認する。

| 指標 | 合格基準 |
|---|---|
| メモリ使用量の増加 | 72時間で10%以内の増加 |
| レスポンスタイムの劣化 | 開始時と72時間後でP95が20%以内の差 |
| エラーレート | 全期間を通じて0.1%未満 |

### 6-3. スロークエリ調査

Auroraのパラメータグループで `log_min_duration_statement` を設定し、100ms以上かかったクエリをCloudWatch Logsに出力する。CloudWatch Logs Insightsでスロークエリを一覧した後、`EXPLAIN ANALYZE` で原因を特定する。`Seq Scan`（全件スキャン）が出ていればインデックスが効いていないサインなので、`Index Scan` になるようにインデックスを追加する。

### 6-4. ツール

| ツール | 用途 | 特徴 |
|---|---|---|
| Locust | ストレス・スパイク・耐久テスト | PythonベースでFastAPIチームがそのまま書ける |
| Lighthouse | フロントエンドの初期表示速度 | Core Web Vitalsを計測 |
| CloudWatch | インフラ監視 | CPU・メモリ・DBコネクション数を計測 |

### 6-5. 計測すべき指標

- レスポンスタイム（平均・P95・P99）
- スループット（RPS: 毎秒リクエスト数）
- エラーレート
- CPUとメモリ使用率（CloudWatch）
- DBのコネクション数・クエリ実行時間

### 6-6. 不合格時の修正方針

不合格になったらCloudWatch・Locustのレポートでボトルネックを特定し、修正後に同じ条件で再テストする。1回で合格することはほぼないため、**最低2〜3サイクル分の時間をスケジュールに確保**しておくこと。

**① DBがボトルネックの場合**

`DatabaseConnections` が上限に近い、またはスロークエリが多発しているとき。

| 対処 | 内容 |
|---|---|
| コネクションプールの調整 | `pool_size` と `max_overflow` を増やす |
| インデックスの追加 | EXPLAIN ANALYZEでSeq Scanが出ているクエリに追加 |
| N+1問題の解消 | `joinedload` や `selectinload` で解消 |

**② ECS Fargateがボトルネックの場合**

`CPUUtilization` が80%を超えているとき。

| 対処 | 内容 |
|---|---|
| タスクのスペックアップ | CPU・メモリを増やす |
| Auto Scalingの閾値を下げる | CPU 80% → 60%に変更 |
| クールダウン時間の短縮 | デフォルト300秒 → 60秒に変更 |

**③ アプリケーションコードがボトルネックの場合**

CPUもDBも問題ないのにレスポンスが遅い場合。同期関数になっているエンドポイントを `async def` に変更する、または重い処理をバックグラウンドタスクに逃がす。

**④ メモリリークの場合（耐久テスト不合格）**

| 原因 | 対処 |
|---|---|
| DBセッションが閉じられていない | `finally` ブロックで確実にセッションをclose |
| キャッシュが無限に積み上がっている | キャッシュにTTLを設定する |
| グローバル変数にデータが蓄積している | グローバル変数へのデータ追加を見直す |

### 6-7. ECS Fargate + Auroraでの注意点

- **Aurora：** コネクション数の上限に注意。FastAPIのコネクションプール設定（`pool_size`, `max_overflow`）が重要
- **ECS Fargate：** Auto Scalingが発動するまでのタイムラグに注意
- **Next.js：** SSRを使っている場合、サーバー側のレンダリング負荷も計測する

> 性能テストは必ず本番相当のStaging環境（ECS Fargate + Aurora）で実施してください。ローカルやCI環境では全く異なる結果になります。
