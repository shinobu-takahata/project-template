AWSをインフラに使用している場合、**性能効率性（Performance Efficiency）**の測定は、標準サービスを組み合わせるだけでかなり高度な自動化が可能です。

JIS X 25023で定義されている3つの副特性に沿って、具体的な測定方法を解説します。

---

## 1. 時間効率性 (Time Behaviour)

「応答時間」や「スループット」を測定します。

* **使用するデータ:**
* **応答時間:** リクエストを受け取ってからレスポンスを返すまでのミリ秒。
* **スループット:** 1秒間あたりのリクエスト処理件数。


* **AWSでの測定ツール:**
* **Amazon CloudWatch Metrics:** * **ALB (Application Load Balancer):** `TargetResponseTime` メトリクスで、平均・最大・パーセンタイル（P99など）の応答時間が自動で出ます。
* **API Gateway:** `Latency` メトリクスがこれに該当します。


* **AWS X-Ray:** * リクエストがどのサービス（LambdaやDB）で何ミリ秒消費したか、ボトルネックを詳細に可視化します。


* **計算の当てはめ:**
* JIS式の「平均応答時間」は、CloudWatchの `Average` 統計をそのまま利用。



## 2. 資源効率性 (Resource Utilization)

「CPU」「メモリ」「ディスク」などのリソースをどれだけ「節約」して使えているかを測定します。

* **使用するデータ:**
* **CPU使用率:** 処理中のCPU負荷（%）。
* **メモリ使用量:** 使用中のメモリ量（GB）。


* **AWSでの測定ツール:**
* **Amazon CloudWatch:** * **EC2:** `CPUUtilization` を標準で取得。
* **Lambda:** `Duration`（実行時間）と設定メモリ量から効率を判断。
* **Container Insights:** ECSやEKSを使っている場合、コンテナごとのCPU/メモリ使用率を詳細に計測。


* **Compute Optimizer:** * 「リソースを使いすぎていないか（オーバープロビジョニング）」をAIが判定してくれるため、資源効率性の評価に直結します。




## 3. 容量 (Capacity)

「同時接続数」や「データ処理量」の限界値を測定します。

* **使用するデータ:**
* **最大処理件数:** システムがダウンせずに耐えられる秒間アクセス数。


* **測定手法（負荷試験）:**
* **Distributed Load Testing on AWS:** AWSが提供する負荷試験用ソリューションです。Fargate（コンテナ）を大量に立ち上げて、一気にシステムへ負荷をかけます。
* **GitHub Actions + k6:** GitHub Actionsから **k6** (負荷試験ツール) を実行し、AWSの環境を叩く構成。


* **計算の当てはめ:**
* JIS式の $X = 最大負荷 / 要求容量$。例えば、「10,000ユーザー耐えるはずが、5,000でエラーが出始めた」なら、容量は0.5（50%）と評価。

## 性能効率性を測定する「黄金構成」

GitHubとAWSを連携させた、おすすめの自動測定フローは以下の通りです。

1. **GitHub Actions:** * コードをマージするたびに **k6** や **JMeter** を実行。
* 「期待する応答時間（例：P95が500ms以内）」を超えたらGitHub上でアラートを出す。


2. **AWS CloudWatch Dashboard:**
* ALBの `TargetResponseTime` と EC2/Lambdaの `Resource Utilization` を並べて表示。
* **「負荷が増えたときに、リソースがどう反応しているか」**の相関を見ることで、スケーラビリティの品質が評価できます。
